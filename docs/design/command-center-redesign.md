**Date:** 2026-09-24 (mockups approved by Owen this date; see "Decisions" below for the open questions he resolved and the Classroomscreen-inspired revision that followed approval)
**Status:** Research + design only. **No application code was changed to produce this document**, with one narrow exception logged here: a comment-only `@deprecated` notice was added to the top of `src/data/boardPresets.ts` per decision #3 below — zero behavior/export/logic change. Otherwise, only files under `docs/design/` (this doc, screenshots, mockups) were created or edited.
**Builds on:** [`docs/architecture/command-center-product-direction.md`](../architecture/command-center-product-direction.md) (2026-09-23) — that doc already did deep, code-verified work on Pillars 1–3 (Display Center, Easy Editing, Teacher Launchpad). This doc does not repeat its research; it takes its findings as given, adds fresh screenshot evidence (including one thing that doc couldn't have caught — see below), and turns both into a concrete zone system, home-screen design, editing model, regression plan, and staged build plan for Owen's approval.

## Decisions (Owen, 2026-09-24 — resolves the "Open questions for Owen" from the first pass of this doc)

The first version of this doc (Parts 1–4 below, largely unchanged as an audit record) ended with 5 open questions. Owen approved the direction and answered all 5; this revision folds those answers through the whole doc rather than only at the bottom, and adds a Classroomscreen-inspired pass (Part 2.0/2.4/2.5) on top of the original mockups, since Owen wants the finished feel to land like classroomscreen.com.

1. **Noise HUD → opt-in, not "maybe remove."** Real feature, ships as opt-in: visible only while a noise-monitoring session is actively running **and** the current screen's config allows it. It must **never** render on Assessment Mode, full stop — not "distraction-free by convention," distraction-free by construction. See Stage 0 in Part 4.
2. **"17 vs 18 tools" → recount, don't re-litigate.** Recounted directly against `src/features/teacher-dock/toolRegistry.ts`: `TEACHER_TOOL_REGISTRY` holds exactly **18** entries today (dashboard, timers, classroom-atmosphere, morning-message, today-prep, curriculum-sync, display-composer, mystery-star, quick-picker, prize-board, random-number, lotto-board, materials, display, omninote, jobs, noise, board-control). The historical "17" is stale and is not used anywhere below as a target. More importantly, per Owen's decision the exact count no longer drives the design at all: the merged `/control` home (2.1) decides what's visible (favorites row + one-tap drawer) vs. demoted based on what that screen's own layout needs, not by hitting a specific number.
3. **`boardPresets.ts` → deprecate now, remove later.** Marked `@deprecated` in a code comment today (see the diff in the final report) — no behavior change. Actual removal is Stage 5 (model consolidation), where the naming collision with `templatePacks.ts` it causes is fully resolved by deleting it.
4. **4-widget cap → removed, replaced by group-as-one-occupant.** The hard `MAX_CONTENT_ZONES = 4` rule from the first pass is gone. Instead, a **widget group** (e.g. a stack of timers) counts as a single occupant of a rail zone for layout/overlap purposes, no matter how many widgets it contains. This is the concrete fix for Owen's own real morning board — message widget + 3 timers (as one group) + music card — which the old hard cap would have made impossible to express as "4 slots, 3 already spoken for by the timer stack alone." See 2.3/2.4 and Part 4 Stage 1/4.
5. **Wireframe fidelity → confirmed correct, no change.** The 3 mockups stay plain wireframes (structure/hierarchy, not visual polish); this revision edits their content/behavior callouts, not their visual fidelity level.

There is no shared layout model — each template is an independent set of pixel coordinates. A teacher customizing a board (adding a widget, resizing one) has no such guardrail, and the Board/Scene/Widget consolidation work already flagged in the product-direction doc confirms this generalizes app-wide.

**The actual worst offender — found in this audit, not yet in the product-direction doc:**

Visually it's a themed "UA HIGH DEFENSE SYSTEM / PLUS ULTRA · DEFEND THE LINE" card with 5 letter-tiles (N‑O‑I‑S‑E) and a "CALM" pill — a jarring style clash against every one of the 9 minimal-light/minimal-dark themes, on every preset, whether the teacher asked for it or not.

The concrete contradiction: **Assessment Mode's own description says "No music or images... distraction-free"** (`templatePacks.ts` line 273/283), and its screenshot (`preset-assessmentMode-1920x1080.png`) still shows the full noise-game HUD in the corner. This is a real, verified violation of a preset's own stated intent — worth flagging to Owen directly, since noise-defense is separate, newer, uncommitted work layered on top of everything the product-direction doc already found. It's effectively an **8th independent display-safety/layering system** (the product-direction doc counted 7 precedence layers plus 5 safety implementations; this HUD is outside that inventory entirely, mounted at the `BoardHostDisplay` level, unconditional).

Also always present on every preset, outside the board canvas and outside any zone: an "Enter fullscreen" button (bottom-left), a "Tap to enable classroom sound" button (bottom-right), and a small colored connection-status dot (bottom-right corner) — four different pieces of always-on chrome, none of them coordinated with each other or with whatever the active preset places near those corners.

### 1B. `/control` — exhaustive map, tap/click counts, duplicates, dead ends

Full structural map (routes, mode composition, dock composition, Inspector section-by-section control counts) was traced directly in code; see the routing diagram and full 18-tool registry table in the research notes folded into this doc's citations below. Key facts:

- **Routing is pure pathname-based**, no query params except `/board-lab?mode=edit`: `/` → redirects to `/control`; `/control` → `TeacherControlShell`; `/display` → `BoardHostDisplay` (bypasses `AppShell`); `/board-lab` → Clean Board editor (Present or Edit mode).
- **Four home surfaces confirmed exactly as Owen described**, and the real composition is even messier than "four surfaces" suggests:
  - `TeachModeShell` — a whole-screen swap (`mode === 'teach'`), chrome-minimal, no dock, no editor.
  - `PresentationHub` — the actual default center column in edit mode; has its own "Present"/"Board" toggle *inside itself*.
  - `TeacherCommandDock` — an 18-tool sidebar (registry says "17" in its own naming/history, but the array literally holds 18 entries today, including `board-control` — worth a direct recount before this number is used as a KPI) that renders `null` unless `mode==='edit'`.
  - `DisplayStudio` — a full-screen overlay (`fixed inset-0 z-50`) launched *from inside* Presentation Hub, with its own separate thumbnail rail + canvas + 6-section Inspector.
  - Plus a **fifth**, not counted in the "four home surfaces" framing: Clean Board's own `/board-lab` route has its *own* dock (`TeacherDockDrawer.tsx`) and its own toolbar (`BoardToolbar.tsx`) — a second, separate dock component, reachable only by leaving `/control` entirely.
- **Two unrelated systems share the word "preset"** and overlapping names ("Morning Arrival," "Assessment Mode"): Clean Board's `templatePacks.ts` (drives `/board-lab` → `/display`) and a completely separate, older `src/data/boardPresets.ts` (8 presets, drives the "Board Control" dock tool's `BoardPresetPanel`, feeds a different `ScreenContents`/`BoardWorkspace` system). A teacher clicking "Assessment Mode" in one place and "Assessment Mode" in the other gets two different, unrelated screens. This is a real, user-facing dead-end/confusion risk, not just internal tech debt.
- **`DisplayStudioInspector.tsx` is 772 lines**, 6 accordion sections (Screen, Content, Widgets, Style, Teacher Notes, Display) plus a separate Widget Detail view — roughly 20–30 individual controls total depending on how many widgets exist on the selected screen. It is the *only* place to resize (preset dropdown, not a drag handle) or delete a widget.
- **Live evidence, captured from this machine's own real Chrome profile** (not a synthetic fresh state — this is what `/control` actually looks like after real use): `docs/design/audit/control-editor-cluttered-example.jpg`. It shows, simultaneously: a "Noise Defense · idle" badge floating over the "Present/Board/Mode" toggle row, half off the visible edge; a "Morning Briefing" preview card overlapping "20 Independent Arrival" and "1. Unpack your" text stacked on top of other text, illegible; a "Reconnecting..." sync badge overlapping the bottom scene-rail tabs; and content extending past the right edge of the window, requiring horizontal scroll to see Display Studio's edge. This is real, current, in-app overlap — not a hypothetical.

## Part 2 — Design (for approval — nothing here is implemented)

### 2.0 Classroomscreen research — what to copy, what doesn't fit

Owen wants Command Center's `/control` editing experience to feel like [classroomscreen.com](https://classroomscreen.com/) once this redesign ships. Researched live via web search/fetch against classroomscreen.com's own site and help center (cited inline; see the final report for the full source list). Summary of how it actually works today:

- **Bottom widget bar, tap-to-add.** "You can find the widget bar at the bottom of every screen" ([Getting started guide](https://classroomscreen.com/blog/the-ultimate-getting-started-guide)); a teacher clicks a widget's icon in that bar and it appears on the canvas — "Click on its icon in the widget bar... A small gray dot appears above the icon" once it's active ([Setting up your screen](https://classroomscreen.com/helpcenter/setting-up-your-screen)). No drag-in from a separate library/sidebar step.
- **Direct-manipulation editing.** Once placed, a widget shows an indigo border; "Resizing: click and drag on any corner," moving is drag-anywhere-on-the-widget or a dedicated drag handle in a floating per-widget toolbar, and a "More" menu adds copy/paste, "Pin" (keep visible across all screens in a deck), "Spotlight" (highlight one, dim the rest), "Lock" (prevent move/delete), and "Layer" (same source).
- **26 widgets** ([Meet the widgets](https://classroomscreen.com/widgets)) spanning time (Timer, Visual timer, Stopwatch, Event countdown, Clock, Timetable), engagement/behavior (Sound level, Randomizer, Group maker, Scoreboard, Poll, Traffic light, Work symbols), content (Image, Video, PDF, Embed, Hyperlink, Webcam, Draw, QR Code), and visual (Backgrounds, Stickers, Text, Dice, Calendar).
- **Screen decks + saved screens.** Multiple screens live in a "deck" a teacher flips through (commonly one deck per day); Pro accounts can save a customized screen/deck and reuse it later, and share it via a link, "which means less daily setup" ([Save and share your screens](https://classroomscreen.com/helpcenter/save-and-share-your-screens); [Replace your daily slides](https://classroomscreen.com/product/replace-your-daily-slides)).
- **No overlap prevention — the opposite, in fact.** Classroomscreen's own "Layer" feature exists specifically to "arrange widget depth and **create overlaps**." Free-for-all placement with manual z-ordering is a deliberate design choice for them.

**What's worth copying into Command Center:** the bottom tap-to-add widget bar (fast, no sidebar hunt — 2.1/2.4 below); true direct-manipulation drag/corner-resize/inline toolbelt (2.2, already planned pre-research, now confirmed as the right target feel); saved/reusable screens replacing rigid built-ins-only presets (2.4); grouping multiple widgets under one manipulable unit (their "Group" feature under "More," independently validated by Owen's own group-as-one-occupant decision, 2.3).

**What does NOT fit, and why:** two things, both load-bearing for Command Center's architecture and explicitly called out here so they are never accidentally "fixed" by copying Classroomscreen too literally:
1. **Free-for-all overlap via manual layering.** Classroomscreen lets widgets overlap on purpose (the "Layer" feature). Command Center's redesign goes the other way on purpose — snap grid + a real-time collision check that blocks/nudges an overlapping drop (2.2/2.3) — because our display is a shared classroom TV a teacher isn't staring at while editing, unlike Classroomscreen's single always-visible canvas; silent overlap on `/display` is a regression here, not a feature.
2. **One shared canvas is both the editor and what students see.** This is the single most important non-fit. Classroomscreen has no analogue to our `/control` vs. `/display` split — the teacher's own editing view *is* the student-facing view, live, all the time. Command Center **deliberately keeps these as two separate surfaces** (`/control` teacher-only, `/display` classroom TV/board) and this redesign does not merge them. What we borrow instead is the *feel* of Classroomscreen's editor — via the WYSIWYG requirement in 2.2, `/control` shows a true-to-scale live copy of exactly what `/display` renders, so editing feels as direct and immediate as Classroomscreen's single-canvas model, without actually exposing the teacher's raw editing state (drag jitter, selection handles, unsaved mid-drag states, the widget bar itself) to students on the TV.

### 2.1 One `/control` home screen

Mockup: **`docs/design/mockup-control-home.html`** (open directly in a browser — MacBook-width frame, the one-tap tool drawer, and an iPad-portrait frame).

Design:
- **Always visible, no scrolling, no mode switch:** live 16:9 display preview, Prev/Next, Blank Display, one Send to Display button, the scene rail (tap a thumbnail = switch screens, 1 tap), and a quick-tool row (teacher's own favorites, swappable) — this is Presentation Hub's good parts and Teach Mode's calm parts merged into one screen that both a first-year teacher and a five-year veteran land on by default. No `mode==='teach' vs 'edit'` full-screen swap.
- **Classroomscreen-style bottom widget bar (new in this revision, per Part 2.0 research):** a persistent strip along the bottom of the live preview, one icon per widget type (Timer, Message, Music, Noise Status, Stamp, QR, etc.). Tapping an icon adds that widget **directly onto the current screen**, landing it in that widget type's default zone (2.3) with the free-placement collision check (2.2) already applied — no drag-in from a sidebar, no intermediate "widget library" screen. This replaces the old "Add Widget" quick-tool button with a purpose-built bar, and is the concrete mechanism behind the mockup's "✎ Edit board" card.
- **One tap away, in a single grouped drawer:** the full tool registry, existing daily/students/instruction/management categories kept — they're already sound, **plus** Clean Board's Spotify/Stamps/QR/routine tools folded into the same categories as new entries (not a second dock), **plus** the Resource Loader as a tab in this same drawer instead of a full-screen mode swap. Per decision #2, this drawer's contents are sized to what the merged home's own layout needs, not to any specific historical tool count — the registry currently holds 18 entries (`toolRegistry.ts`, recounted directly, see the Decisions section above), and that number is reported here as a fact about today's code, not as a design target this drawer must hit.
- **Rare settings, two taps, never on the main screen:** background/theme picker (one place, not three), device pairing, backup/restore.
- **On-canvas editing entry point** lives right on the home screen ("✎ Edit board" card) — no separate "Display Studio" destination to discover. Editing here is WYSIWYG (2.2): the live preview a teacher edits **is** a true-to-scale copy of the `/display` output, not an abstracted mini-map of it.

This directly implements the product-direction doc's own recommendation ("merge, not replace or coexist") and Owen's ask (one home, common tasks in ≤2 taps, no scrolling at MacBook/iPad sizes). The mockup's task audit: switch screen 1 tap, blank 1 tap, send 1 tap, start a favorited timer 1–2 taps, open noise game 1 tap (favorited) or 2 (drawer), add a widget **1 tap** (bottom widget bar — down from 2 in the prior pass, since there's no intermediate widget tray screen anymore), change background 2 taps (Settings, one place).

### 2.2 Editing model — WYSIWYG, on-canvas, dnd-kit

Mockup: **`docs/design/mockup-editing-model.html`**.

- **WYSIWYG, not an abstraction (new emphasis in this revision):** `/control`'s editor renders a true-to-scale live copy of exactly what `/display` shows — same aspect ratio, same widget rendering, same fonts/sizes at scale — so what the teacher sees while editing is pixel-exact to what's on the classroom TV, not a schematic or a simplified stand-in for it. This is what makes the editor feel like Classroomscreen's single-canvas directness (2.0) while still keeping `/control` and `/display` as genuinely separate surfaces: the teacher edits a faithful copy, students never see the editing chrome (toolbelts, handles, the widget bar) because that chrome only exists on the `/control` copy, never on `/display`'s own render.
- **Select:** tap/click the widget directly (no separate "select tool").
- **Move:** drag anywhere on the widget body. Built on `dnd-kit`'s `useDraggable`/`useDroppable` (already a dependency, confirmed in the product-direction doc) with pointer events (not the current mouse-only `onMouseDown`/`mousemove`) — this is the concrete fix for "doesn't work on iPad."
- **Resize:** drag a corner handle, paired with a small dedicated resize component (or `re-resizable`, same library `react-rnd` wraps) per the product-direction doc's own recommendation — not react-rnd wholesale (maintenance risk flagged there) and not Konva (documented mismatch for interactive DOM widgets like a running timer).
- **Delete / duplicate / lock:** an inline toolbelt that appears on selection, directly on the widget — plus a Delete-key shortcut.
- **Quick edit:** double-tap opens a small anchored popover for content-only fields (text, timer minutes, image URL) — this is what's left of the Inspector for the common case.
- **Widget-specific settings that don't fit inline** (noise-game mode/level, routine ID) get a short single-purpose sheet scoped to that one widget — not the current 772-line, 6-section, always-open Inspector.
- **Free placement on a snap grid, with automatic overlap prevention (revised from "snap-to-zone, no overlap allowed"):** a teacher is not limited to the 5 zone rects — they can drag a widget anywhere there's room on the underlying grid, and the drag snaps to the nearest grid line as it moves. The 5 zones from 2.3 are **smart default landing positions** per widget type (a newly-added timer proposes rail-1, a newly-added message proposes main, etc.), not hard placement limits. What *is* still hard, by construction: a real-time collision check runs on every drag/resize/drop and **blocks or nudges** a placement that would overlap another widget's (or group's — see below) current rect. This is the corrected version of decision #4/#1's collision guarantee: overlap is prevented by the grid + collision check itself, not by confining widgets to 4 fixed boxes.
- **Widget groups behave as one occupant.** A group (e.g. Owen's real-world stack of 3 timers) is dragged, dropped, and collision-checked as a single rectangle — internally it still contains 3 independent timers a teacher can expand and edit individually, but for placement/overlap/zone-occupancy purposes the whole group is one thing occupying one rail slot. This directly replaces the old hard 4-widget cap (2.3): the constraint that matters is "can this rectangle fit without overlapping," and a group is exactly one rectangle no matter its internal widget count.

### 2.3 `/display` zone-based layout system

Mockup: **`docs/design/mockup-display-presets.html`** — the zone rules plus 3 fully redesigned presets (Morning Arrival, Math Workshop, Assessment Mode) rebuilt on the shared grid.

- **5 zones remain, but now as smart defaults, not hard slots (revised from the first pass):** `title` (full width minus rail, top), `main` (message/content, left ~66%), `rail-1` + `rail-2` (right ~26%, two stacked slots), `system` (one reserved 40px strip at the bottom edge for fullscreen/sound/connection chrome — always the same place, never mixed into content), all sitting on top of the same 1920×1080 logical canvas, 56px safe margin, and a finer snap grid underneath them (2.2). Each zone is where a given widget *type* lands by default when added from the bottom widget bar (2.1/2.4) — a teacher can still drag it anywhere else on the grid where the collision check allows it.
- **No hard widget-count cap (decision #4 — replaces the old "4 content slots" rule).** The old `MAX_CONTENT_ZONES = 4` structural limit is removed. In its place: overlap is prevented by the snap grid + collision check (2.2), and a **widget group counts as one occupant** of a rail zone regardless of how many widgets it contains. Owen's own real morning board — a message widget, a group of 3 timers, and a music card — is the concrete case this must support: under the old cap, the 3-timer group alone could have been read as 3 of the 4 slots; under the new rule it's correctly 1 occupant (the group) alongside the message and the music card, 3 occupants total, with room to spare.
- **The status/game widget (what today is the unconditional Noise Defense HUD) becomes an explicit, optional occupant of one rail slot** — a teacher turns it on for a specific screen, it never appears uninvited, and it can never coexist with a music widget in the same slot. This is the direct, concrete fix for the Assessment Mode contradiction found in Part 1, refined further under decision #1: it also only renders while a noise-monitoring session is actively running, even on a screen that allows it — "opted in" is necessary but not sufficient, an idle session shows nothing.
- **Multi-timer routines collapse into one group** ("Step 1 of 3 — Quiet Morning Work, 24:12") instead of 3 stacked boxes — fixes Morning Arrival — New Classroom's rail, and is the worked example of the group-as-one-occupant rule above.
- **Minimum type scale, clamped in the data model, not just a Tailwind convention:** title ≥64px, main heading ≥40px, main body ≥32px, timer digits ≥56px, status/system text ≥20px. This is exactly the fix the product-direction doc already recommended for Clean Board's uncla­mped `fontSize`/`titleSize`/`bodySize` inputs, expressed as a zone-system-wide floor rather than a single patch.
- **Free placement + snap grid + overlap prevention, zones as defaults** — see 2.2 for the full mechanism; this section defines the default landing zones the mechanism targets.
- Each of the 9 built-in presets gets rebuilt on this grid (3 shown in the mockup as worked examples; the same transform applies mechanically to the other 6 — heading→title zone, message→main zone, timer(s)→rail-1 as a group if multiple, optional Spotify→rail-2).

### 2.4 Saved screens (replaces "built-in presets only")

Extends the mockups (scene-rail card in `mockup-control-home.html`) with the Classroomscreen "save your screens" model (2.0): a teacher can save the *current* layout of any screen — whatever widgets/groups/positions are on it right now, whether it started from a built-in template or was hand-built — as a named, reusable screen (e.g. "Morning," "Math," "Reading"), and re-select it later from the same scene rail alongside the built-ins. This is additive, not a replacement for the 9 built-in presets from 2.3 — those remain as starting points/defaults — but it removes the "presets are the only screens that exist" rigidity: a teacher's own saved screens are first-class, sit in the same picker, and are what most teachers will actually use day to day once they've customized a few. No account/sharing tier is implied here (Classroomscreen gates saving behind Pro; Command Center has no such tier today) — this is scoped as local, teacher-owned saved screens, not a sharing/publishing feature.

## Part 3 — Regression plan

Following this repo's existing conventions: Playwright specs under `tests/e2e/*.spec.ts` run via a `scripts/test-*.sh` wrapper registered as an `npm run test:*` script (see `test:display-snapshots` → `display-snapshots.spec.ts`), and pure-logic checks compiled with `tsc` and run directly under `node` (see `scripts/test-synthesizer.sh`) for anything that doesn't need a browser.

1. **Static per-preset overlap guard (unchanged from the first pass): `tests/e2e/display-zone-overlap.spec.ts` → `scripts/test-display-zone-overlap.sh` → `npm run test:display-zone-overlap`.**
   For every built-in preset id, apply it (same flow as `display-snapshots.spec.ts`'s template application), navigate to `/display` at 1920×1080, then assert via `page.evaluate`: collect every zone-slot-occupying widget's (or widget-group's — one bounding rect per group, not per member) `getBoundingClientRect()`, and fail if any pairwise rectangle intersection is non-zero. This is a direct port of the exact overlap check used for this audit's screenshot capture (pairwise AABB intersection test) into a permanent CI-shaped guard, run against every preset id in `TEMPLATE_PACK_IDS`, not just the 3 shown in the mockup. This test alone only proves the *built-in, static* presets don't overlap — see the next point for the gap that leaves.
1a. **Edit-time overlap guard (new in this revision, closes the gap above): `tests/e2e/control-edit-overlap.spec.ts` → `scripts/test-control-edit-overlap.sh` → `npm run test:control-edit-overlap`.**
   Since the redesign moves from "widgets can only sit in 4 fixed rects" to "free placement on a snap grid with a live collision check" (2.2), the overlap guarantee now has to be proven for *editing*, not just for static built-ins. This spec drives the actual `/control` editor (dnd-kit pointer events) to: (a) drag a widget to a position that would overlap another widget/group and assert the drop is blocked or nudged to a non-overlapping snapped position, never silently allowed; (b) drag a widget group (e.g. a 3-timer stack) and assert it moves/collision-checks as one rectangle, not three; (c) resize a widget via corner handle into another widget's space and assert the same block/nudge behavior. Both this live behavior test **and** the static per-preset test above must pass — one proves the mechanism works during editing, the other proves the built-in content that ships by default is clean; neither replaces the other.
2. **Visual snapshots of every preset**, extending the existing `display-snapshots.spec.ts` pattern (`toHaveScreenshot`) with one baseline per template id at 1920×1080 (currently that spec only covers the fallback default, a stamp card, and a QR card — not the 9 template presets at all). Add to the same file rather than a new one, consistent with its existing `describe` block structure.
3. **Layout rules enforced in code, not by convention:**
   - A `ZoneId` union type (`'title' | 'main' | 'rail-1' | 'rail-2' | 'system'`) and a `ZONE_RECTS: Record<ZoneId, Rect>` constant define the **default landing position per widget type** — no longer the *only* place a widget may live (revised from the first pass, per decision #4). `ClassroomTemplatePack`'s built-in content still keys off a `zone: ZoneId` field for its defaults, but the underlying placement model is a snap grid a widget/group can occupy anywhere on, subject only to the collision check.
   - The `MAX_CONTENT_ZONES = 4` hard cap is **removed** (decision #4). In its place: a `WidgetGroup` concept whose bounding rect is what the collision check and any occupancy accounting operate on — a group of N widgets is always 1 occupant, never N. There is no fixed maximum occupant count; the only runtime rule is "reject/nudge a placement whose rect intersects another occupant's rect."
   - Minimum-font-size clamps as validation in the shared `WidgetSettings` type (already recommended in the product-direction doc for Pillar 1) — extended here to cover all 5 zone type-scale floors, not just body text.
   - A pure-logic unit test (`scripts/test-zone-layout.sh`, `tsc` + `node`, no browser) asserting the 5 default `ZONE_RECTS` are pairwise non-overlapping and each fits inside the 1920×1080 canvas minus the 56px margin, **plus** a grid-collision pure-logic test asserting the collision-check function itself correctly flags overlap for arbitrary (non-zone-aligned) rect pairs and correctly ignores non-overlapping ones — a static geometry proof, independent of any rendered screenshot, and cheap enough to run on every commit.
4. **Tap-count checklist** — a maintained markdown table (this doc's Part 1B table, kept alongside a "target" column from Part 2) re-verified by hand each time `/control`'s home screen or editing model changes; not automatable the way overlap/snapshots are, but the specific tasks to re-check every time are: switch screen, start a timer, blank the display, add a widget, move/resize/delete a widget, edit text, open the noise game, change the background — the same 8 tasks audited above, so regressions in tap-count are caught by comparing against this doc rather than reinvented per change.

## Part 4 — Staged build plan

Ordered so the app stays usable and default-branch-shippable at every step — no stage leaves `/display` or `/control` broken mid-way. Numbering follows on from the product-direction doc's own dependency-ordered sequence (its steps 1–3 are cheap/isolated fixes that should land before this plan's Stage 1, since they're smaller and already fully scoped there — touch support on the existing drag, collapsing the duplicate Send-to-Display button, the `toggleWidgetLibrary` bug, the Clean Board font-size floor).

**What changed from the first pass, and why:** Stage 0 is unchanged in position (still first) but its description is sharpened to the exact opt-in behavior Owen specified (decision #1) instead of a generic "gated behind a flag." Stage 1 now builds `ZONE_RECTS` as *defaults* plus a `WidgetGroup` primitive instead of a hard 4-slot cap, since decision #4 removes the cap before Stage 1 even ships — building the cap first and ripping it out in Stage 4 would have been wasted work. Stage 3 is retitled and expanded to explicitly include WYSIWYG rendering and free-placement/snap-grid dragging (2.2), not just resize handles, since that's now the core of the editing-model ask, not an add-on. Stage 4 is retitled from "Snap-to-zone + the 4-widget cap" to "Free placement + collision guard," reflecting decision #4 directly — there is no cap left to enforce, only the collision check. A new **Stage 4.5** is added for saved screens (2.4), since that's new scope from this revision that didn't exist in the first pass and has a clear dependency on Stage 3's editor existing first. Stages 2, 5, and 6 are otherwise unchanged in position and intent.

- **Stage 0 (do first, smallest, highest-value): make the Noise Defense HUD an explicit, opt-in, per-screen widget instead of an unconditional overlay.** Refined per decision #1 to the exact behavior required, not just "gated behind a flag": the HUD renders **only when both** (a) a noise-monitoring session is actively running, **and** (b) the current screen's config has opted in to showing it — and it must be structurally impossible for it to render on Assessment Mode (either by Assessment Mode's config never allowing the opt-in, or by an explicit denylist check independent of per-screen config, whichever proves more robust when this is implemented). This is a single-file change (`BoardHostDisplay.tsx` line 71) — it's the single highest-leverage fix found in this audit, it directly resolves the Assessment Mode contradiction, and it doesn't depend on anything else here.
- **Stage 1 — Zone geometry for the 9 built-in presets, without touching the editing UI.** Introduce `ZONE_RECTS`/`ZoneId` as **default** landing positions (not hard slots) and a `WidgetGroup` primitive whose bounding rect is what overlap-checking operates on, migrate `templatePacks.ts`'s `createTemplateObjects` to place objects by zone instead of hand-picked x/y, collapse multi-timer sequences into one group. Add the static overlap-guard and visual-snapshot tests from Part 3 against this new geometry. **No hard cap is introduced here** (revised from the first pass, per decision #4) — the group primitive and the "count is unbounded, only collision matters" rule are built in from this stage forward. The app stays fully usable throughout — teachers see the same 9 presets, now laid out consistently, before any editor change ships.
- **Stage 2 — `/control` home-screen merge, UI composition only, no data-model change.** Build the single home screen (2.1) as a new component that composes Presentation Hub's preview/actions/scene-rail with the dock's favorites row, the drawer, and the new bottom widget bar (2.1/2.0); retire the `mode==='teach'` full-screen swap in favor of this one screen; fold Clean Board's Spotify/Stamps/QR tools into the shared registry as launch points (they can still open Clean Board's own panels underneath — no store migration required yet, per the product-direction doc's own "can be built now" callout for exactly this). Per decision #2, the drawer's contents are sized to the merged home's own design, not to a hardcoded tool count. This is additive/compositional, matching the product-direction doc's step 2.
- **Stage 3 — WYSIWYG on-canvas editing (dnd-kit, free placement, resize), additive to the existing Display Studio canvas (expanded scope from the first pass).** Make the `/control` editor render a true-to-scale live copy of `/display`'s own output (2.2's WYSIWYG requirement), then add touch-capable free-placement drag on the snap grid, corner-resize handles, the inline toolbelt, and the quick-edit popover to the *existing* canvas and data model — the product-direction doc is explicit this doesn't need to wait for consolidation. Ship with the Inspector still present as a fallback/advanced view until Stage 3 is validated, then trim it down to widget-specific-only settings.
- **Stage 4 — Free placement + automatic overlap prevention, enforced for teacher-authored (not just built-in) screens (retitled from "Snap-to-zone + the 4-widget cap," per decision #4).** Wire the drag/resize interaction from Stage 3 into the snap grid + collision-check mechanism from Stage 1/3, including group-as-one-occupant behavior, so a teacher's own edits get the same overlap-proof guarantees the built-in presets already have. Add the new edit-time overlap test (Part 3, item 1a) here, alongside the existing static test. This is the stage that turns "no built-in preset overlaps" into "no screen this app can produce overlaps" — with no widget-count ceiling anywhere in that guarantee.
- **Stage 4.5 — Saved screens (new stage in this revision, 2.4).** Once Stage 3's editor and Stage 4's placement guarantees exist, add "save current layout as a named screen" + a picker that lists saved screens alongside the 9 built-ins in the same scene rail. This depends on Stage 3 (there has to be an editor to save *from*) and is sequenced right after Stage 4 so saved screens inherit the overlap guarantee rather than being a second, unguarded path to a bad layout.
- **Stage 5 — Board/Scene/Widget consolidation** (already the long pole in the product-direction doc's own plan, Strangler-Fig style, starting with Display Composer) — everything above should be built to survive this migration rather than wait for it, exactly as that doc recommends. Once done, the two colliding "preset" systems (Clean Board's `templatePacks.ts` vs. `boardPresets.ts`) collapse into one — `boardPresets.ts` (marked `@deprecated` now, per decision #3) is deleted here, resolving the naming-collision dead end found in Part 1B.
- **Stage 6 — only after Stage 5:** Resource Loader persistence, then new widget types — per the product-direction doc, building either against a model about to be replaced is the one sequencing mistake most worth avoiding. The Classroomscreen gap list from 2.5 (Stopwatch, Group maker, Traffic light, Dice, Poll, Stickers/Draw, Image/PDF/Embed/Webcam) feeds this stage's backlog alongside the previously-flagged video widget — none of it is scoped or committed to yet, just recorded so this stage starts from a real list.
